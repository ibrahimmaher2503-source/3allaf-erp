# 06 — User Flows

## Platform Guidance Flows — TSK-004B

`FLW-UI-01`, `FLW-HELP-01`, and `FLW-HELP-02` are defined in `docs/40-contextual-page-guide-specification.md` and implemented in the shared UserFlowRegistry. They are documentation flows only and do not redefine business behavior.

## Flow Contract

Every flow below inherits these rules: authenticate and resolve role/branch/store/activity scope; load only authorized records; validate on the server; prevent duplicate submission; enforce allowed state transitions; use a database transaction and locking/idempotency for document, stock, payment, wallet, loyalty, gift-card, shift, number, or synchronization effects; preserve approved history; append required audit; and return complete responsive RTL/LTR UI states. `None` under effects means the flow must not create that type of effect.

State names explicitly listed by the PRD are mandatory. Additional workflow state names used to make a flow implementable are **Proposed** and require owner approval before implementation; they do not create a confirmed business rule.

## Cross-Flow Blocked Transitions

- Any approved/final/closed document back to editable draft.
- Any direct ledger or stock-balance edit.
- Any retail document accepting a party line, or party document accepting a retail line.
- Any cross-wallet view, settlement, transfer, or correction without a new approved requirement.
- Any Stock Counter approving reconciliation.
- Any Cashier seeing expected close totals before blind submission.
- Any sale of non-assigned store stock or unpriced product.
- Any offline credit, wallet, loyalty redemption, special discount, or policy-expired operation.
- Any quotation posting stock, reservation, payment, wallet, or accounting effects, or converting in Phase 1.
