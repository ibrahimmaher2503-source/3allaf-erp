## 1. Purpose and Scope

`stock_movements` and `audit_logs` are the two tables that will reach millions of rows, and almost every read surface in the system derives from them. This document defines how tables, queries, lazy loading, and caching behave at that scale.

NFR-05 requires safe loading on high-volume views. This is the implementation of that requirement.

**Deliberate scope limit.** Everything in §11 and §12 is deferred until measurement justifies it. Building distributed complexity before the data exists is the more common failure, and it is more expensive to undo than to add. The three items in §13 are the only ones worth doing before volume arrives.

## 2. Data Model Rules

### 2.1 Types

| Rule | Reason |
|---|---|
| `DECIMAL(19,4)` for money everywhere, including temporary aggregate columns | Floating point loses cents silently (`docs/09` §45) |
| `DECIMAL(20,6)` for quantity | Fractional products (INV-06) |
| `ENUM` for movement types, document states | Engine-level validity, smaller index |
| `utf8mb4_unicode_ci` for Arabic text | Correct collation for search and sort |
| `utf8mb4_bin` for barcodes, item codes, document numbers | Exact matching; no case or accent folding |
| `RESTRICT` foreign keys on financial documents, never `CASCADE` | A cascading delete on an approved invoice is unrecoverable |
| `InnoDB`, `READ COMMITTED` isolation | Fewer gap locks under concurrent posting than the default `REPEATABLE READ` |

### 2.2 Indexes

Composite index column order follows the query, not the schema:

| Table | Index | Serves |
|---|---|---|
| `stock_movements` | `(store_id, product_id, posted_at)` | Stock card, ledger reads |
| `stock_movements` | `(source_type, source_id)` | Document drilldown |
| `stock_movements` | `(posted_at)` | Period reports |
| `stock_movements` | unique `(idempotency_key)` | Repost protection |
| `stock_balances` | unique `(product_id, store_id)` | Balance lookup |
| `audit_logs` | `(source_type, source_id, created_at)` | Document history |
| `audit_logs` | `(request_id)` | Support correlation |
| `purchase_invoice_lines` | `(purchase_order_line_id)` | PO matching — `DEC-043` A-01 |

Covering indexes are used where the read is hot: adding `quantity` and `unit_cost` to the stock-card index lets the query resolve from the index without touching the table.

Generated columns carry the indexed form of any expression used in a filter. `WHERE YEAR(posted_at) = 2026` cannot use an index; a generated `posted_year` column with its own index can.

### 2.3 Derived state

`stock_movements` is the truth. `stock_balances` is a projection.

A current balance is **never** computed with `SUM()` over movements. That query gets slower every day the business operates. Movements answer history; balances answer now.

## 3. Period Snapshots

The single highest-value structural addition, and the cheapest to add before data exists.

A `stock_period_snapshots` table stores quantity and value per product/store at each period close.

```
report for March = snapshot at end of February
                 + movements within March
```

Without snapshots, every historical report scans from the beginning of the ledger. With them, the scan is bounded to one period regardless of how long the business has been running.

Rules:

1. Snapshots are generated by a scheduled job after period close and are immutable once written.
2. A snapshot must be reproducible: rebuilding it from movements must produce the identical figure. A reconciliation job proves this.
3. A backdated correction after a snapshot exists invalidates that snapshot and every later one; they are regenerated, never edited.
4. Snapshots carry the same cost precision as the ledger (`DECIMAL(19,4)`).

## 4. Query Practice

| Rule | Instead of |
|---|---|
| `select()` the displayed columns | `SELECT *`, which drags `TEXT` columns into memory |
| `cursorPaginate()` above ~50k rows | `paginate()` with large `OFFSET`, which reads and discards every skipped row |
| `simplePaginate()` when the last page number is not needed | A `COUNT(*)` that often costs as much as the page query |
| `chunkById()` | `chunk()`, which skips or repeats rows when the set mutates mid-iteration |
| `withCount()` | `->relation->count()` inside a loop |
| `EXISTS` | `IN (subquery)` on MySQL |
| `upsert()` for bulk import | A loop of `updateOrCreate` |
| `JOIN` against a temporary table | `whereIn` with a very large array |
| `lazy()` / `cursor()` in export jobs | `get()` on an unbounded result |

Sorting rules:

1. Sort only on indexed columns. A sort on a computed expression or a joined aggregate forces a filesort over the whole set.
2. If a business sort like "top by sales" is required, it reads a materialised column, not a live `SUM()`.
3. Every sort carries a tie-breaker (`ORDER BY posted_at DESC, id DESC`). Without one, equal rows reshuffle between pages and users see duplicates or gaps.

Search rules:

1. `LIKE 'term%'` uses an index; `LIKE '%term%'` does not.
2. Barcodes, item codes, and document numbers use exact or prefix matching only.
3. Product name search uses FULLTEXT or a normalised search column — never an unanchored `LIKE` on a large catalog.

`EXPLAIN` is run on every report query before it ships.

## 5. Filtering

1. **Allow-list every filter and sort key.** A name arriving from the query string is matched against a permitted set before it reaches `orderBy` or `where`. Passing it through directly is both a performance and an injection problem.
2. **A default date range is mandatory** on ledger and report tables — proposed 30 days, expandable by the user. No table opens on the entire history.
3. **Filters live in the URL** (`#[Url]`) so a filtered view can be shared and returned to.
4. **Changing any filter resets to page 1** (`resetPage()`), or the user lands on an empty page and believes the data is missing.
5. **Scope is applied before the filter, always server-side** (NFR-03). A branch filter narrows within the user's scope; it never widens it.

## 6. Livewire Behaviour

| Attribute / directive | Use |
|---|---|
| `#[Computed]` | Any large result set — a Livewire property is serialised into every request |
| `#[Locked]` | Every property holding an ID or a scope value; otherwise the client can change it |
| `#[Url]` | Filters, sort, page |
| `#[Lazy]` | Heavy tables, so the shell and filters paint first |
| `wire:key` | Every row in a loop — without it the DOM misbinds on sort and delete |
| `wire:model.live.debounce.500ms` | Search inputs only |
| `wire:model.blur` | All other text inputs |
| `wire:loading.delay` | Suppresses the flicker of sub-200ms operations |
| `wire:navigate` | Navigation without full reload |
| `$this->dispatch()` | Cross-component communication — never pass collections between components |

**Known trap:** `#[Lazy]` combined with an uncached computed query executes the query twice — once for the placeholder resolution path and once for the real render. Verify each table issues its query once, using the query log, not by inspection.

## 7. Table UI at Scale

**Structure**

- Sticky header; sticky first column on wide tables (right-hand side in Arabic).
- Priority columns: lower-priority columns collapse into a detail drawer on narrow viewports — already required by the shared screen contract in `.ai/UI_SCREENS.md`.
- User-configurable visible columns, persisted through the existing `user_ui_preferences`.
- Rows are clickable in full, not through a small trailing icon.

**Numbers**

- Right-aligned, with `tabular-nums` so digits align in a column.
- Footer shows both page total and grand total, explicitly labelled as different figures.
- Above a configured threshold the result count may be approximate — "more than 10,000" — because an exact `COUNT(*)` over millions of rows costs more than it informs.

**Feedback**

- Skeleton matching the final table shape, not a spinner.
- Active filter count visible with a clear-all control. "The report is empty" is the most common ERP complaint and is nearly always an unnoticed filter.
- Empty, loading, error, and permission-denied use the shared state components (`docs/49` §7).

**Bulk actions**

- "Select all" selects **the current page**. The distinction must be stated in the UI, with an explicit "select all N results" option.
- Cross-page selection is held as a set of IDs, and the action runs as a queued job with progress.

**RTL**

- Table direction mirrors; sort arrows and pagination controls mirror.
- Numbers, barcodes, and document numbers stay LTR inside Arabic text.
- Meaning icons (printer, clock) do not mirror; directional icons do.
- Mixed-content fields use `dir="auto"`.

## 8. Lazy Loading

Four levels, each with a different trigger:

| Level | Mechanism | When |
|---|---|---|
| Component | `#[Lazy]` with a shaped `placeholder()` | Heavy tables and dashboards |
| Column | Second-pass load for expensive columns | Computed balances, last cost |
| Tab | Load on activation | Stock card movement tab, product supplier tab |
| Progressive list | Load-more on scroll | Visual browsing surfaces such as POS product selection |

Pagination is preferred over infinite scroll on report tables: an operator needs to know their position in the result set and be able to return to it.

**N+1 is the dominant table performance defect.** `Model::preventLazyLoading()` is enabled in local and staging so an unguarded relation access raises immediately rather than surfacing as a slow page in production. Every displayed relation is eager-loaded with `with()`; every displayed count uses `withCount()`.

## 9. Caching

### 9.1 Layers

| Layer | Contents | Lifetime |
|---|---|---|
| Request | A query result reused within one request | The request |
| Application | Categories, brands, settings, permission definitions | Hours |
| Aggregate | Dashboard and report aggregates | Minutes |
| Build | Config, route, view caches | Until next deployment |

### 9.2 Invalidation by version

Keys embed a version rather than being hunted down and deleted:

```
balance:{store}:{product}:v{version}
```

Incrementing the version invalidates implicitly. `stock_balances` already carries a `version` column, so this needs no new state.

Where Redis is available (BLK-001), cache tags allow a scoped group flush: `Cache::tags(['reports', "store:{$id}"])`.

### 9.3 Stampede protection

When a hot key expires, concurrent requests all rebuild it simultaneously. Either take `Cache::lock()` around the rebuild, or use `Cache::flexible()` to serve the stale value while one worker refreshes.

### 9.4 What is never cached

1. Current balance at posting time — read from source under `lockForUpdate()`.
2. Any figure a posting decision depends on.
3. Authorization decisions. Permission **definitions** may be cached; the **decision** is evaluated live on every action (NFR-03).
4. Anything user-specific without the user's ID and scope in the key.

### 9.5 The scoping rule

**Every cache key for permission-filtered data must include the requesting user's scope.**

A key such as `products:list` returns one cached result to every user, which means one branch's data served to another. This is a data-leak class defect, not a performance concern. Scope is part of the key, always.

### 9.6 Read-your-writes

If a read replica is introduced (§11), the request immediately following a write reads from the primary. Otherwise a user approves a document and then does not see it.

## 10. Background Work

1. Exports above a configured row count run as queued jobs; unbounded synchronous export is prohibited (NFR-05, `docs/50` §9).
2. Export jobs stream with `lazy()` or `cursor()` — one row in memory, not the whole result.
3. CSV and Excel cells beginning with `=`, `+`, `-`, or `@` are written as text. Formula injection is an export-side vulnerability, not only an import-side one (`docs/42` §4).
4. Separate queues by priority: posting work must never queue behind a million-row export.
5. Job middleware: `WithoutOverlapping`, `RateLimited`, `ThrottlesExceptions`.
6. Jobs carry the IDs and state they need. `SerializesModels` re-fetches at execution time and fails if the record changed or was removed.
7. Batch imports use job batching with `then` / `catch` / `finally` so progress and cancellation are real.
8. The correlation ID from `SetRequestId` propagates into jobs and audit records.

## 11. Deferred — Introduce Only on Measured Need

These are correct techniques at the wrong time. Each is recorded so the option is known, not so it is built now.

- **Partitioning** `stock_movements` and `audit_logs` by month or quarter. The real benefit is `DROP PARTITION` for retention instead of a table-locking `DELETE`.
- **Read replica** for reporting, with posting kept on the primary. Requires the read-your-writes rule in §9.6.
- **Materialised aggregates** updated incrementally on posting, paired with a nightly reconciliation that recomputes from source and compares. The reconciliation is what makes the aggregate trustworthy; without it, the aggregate is a rumour.
- **Outbox pattern** — write the event inside the posting transaction, let a worker fan out to alerts, notifications, and aggregates. Prevents side effects from breaking the posting transaction and prevents lost events.
- **Bitemporal settings** — store both when a fact was effective and when it was recorded, so "what did the balance look like on 31 March, as known on 31 March" is answerable. Auditors ask this.
- **Advisory locks** (`GET_LOCK`) to serialise a logical operation without locking rows.
- **Atomic balance updates** via `INSERT ... ON DUPLICATE KEY UPDATE on_hand = on_hand + VALUES(delta)`, eliminating the read-modify-write cycle.
- **Online schema change** (`ALGORITHM=INPLACE` or `pt-online-schema-change`) for altering large tables without downtime.
- **Circuit breaker** around printing and file services; **backpressure** rejecting new requests when the posting queue exceeds a threshold.

## 12. Observability

1. Structured JSON logging, filterable, with the correlation ID on every line.
2. Slow query log enabled from day one, not switched on after an incident.
3. `DB::listen` in local and staging fails the request above a query-count budget per screen — this catches N+1 before production.
4. `information_schema.INNODB_TRX` is the first thing to inspect when the system stalls: it shows long-running transactions and live locks.
5. Buffer pool sizing is the single most consequential MySQL setting; it is part of the production infrastructure decision under BLK-001.

## 13. What To Do Now

Three items are cheap today and expensive after volume arrives. Everything else in this document waits for measurement.

1. **Composite indexes** in the first migration (§2.2).
2. **Period snapshot table** created with the ledger, even before the generating job exists (§3).
3. **`inventory:rebuild-balances`** — a command that rebuilds `stock_balances` from `stock_movements` and reports any divergence (`docs/47` §5). This is the strongest diagnostic the system will have, and it is a few hours of work before there is data to reconcile.

Testing note: performance is verified against realistic volume — on the order of 50,000 products and 1,000,000 movements. A screen that performs well on 100 seeded rows demonstrates nothing. Any table exceeding 500ms at that volume is reviewed before release.

## 14. Manual Browser Verification

Verify at realistic volume: cursor pagination holds constant response time at page 1 and at page 2,000; sorting on an indexed column is fast and on a non-indexed column is unavailable; equal-value rows do not reshuffle between pages; a filter change returns to page 1; the default date range applies on first load; active filter count and clear-all are visible; sticky header and first column behave in RTL and LTR; numbers align with tabular figures; page total and grand total are distinguishable; "select all" states whether it means the page or the result set; an export above the threshold queues rather than blocking; a formula-prefixed cell exports as text; a lazy table issues its query once; `preventLazyLoading` raises on an unguarded relation; a cached list for user A is not served to user B in another branch; a balance read during posting comes from source rather than cache; rebuilt balances match stored balances exactly.

No automated tests are created or executed.
